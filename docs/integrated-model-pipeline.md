# Integrated local model pipeline

The current project's API, chat storage, frontend, SAR analysis, change analysis, vegetation analysis, and other question routes remain authoritative. `backend/app/services/integrated_analysis.py` dispatches only single-image optical water, land-cover, and building requests to the copied surface pipeline in `backend/satquery_engine`; all other requests run through the current project's `backend/app/services/orchestrator.py`. Single-image SAR, paired optical/SAR, and temporal analyses always use the current project. No frontend from `D:\Sat1` was copied.

All inference reads checkpoints from this project's `models/` folder by default. Runtime setup creates `backend/.venv-integrated` inside this project. `D:\Sat1` is only the source of the copied surface implementation and optional reference imagery for verification; the application does not require it to start. `/api/v1/models/status` shows the current model inventory plus the five surface specialists. A checkpoint being installed does not prove that it ran for a result; read `models_used`, the trace, and `analysis.json` for that.

The imported surface pipeline routes by verified bands, resolution, and sensor metadata. RF-DETR is the default building instance model on compatible RGB imagery. Compatible georeferenced aerial RGB now requires object-level agreement between FLAIR-HUB and Deepness before publishing a water polygon; disagreement is recorded and withheld. If the compatible aerial models fail, water boundaries are withheld rather than replaced by a potentially misleading RGB proxy. Deepness supplies dense land classes, while confident FLAIR-HUB bare/pervious ground, grass, agriculture, and woodland predictions fill otherwise unclassified pixels. Unclassified surface has its own visible amber color and is not labeled as soil. Exact ten-band Sentinel-2 uses the SatQuery water bundle; compatible named six-band Sentinel-2 can use the giswqs water model. Other surface inputs use documented spectral or RGB proxy methods. Unknown bands, missing georeferencing, missing model runtime, or disputed evidence produce limitations or abstention. Arbitrary open-ended questions cannot have guaranteed accurate answers without validated evidence.

The dashboard selects the overlay for the requested task. A land-cover request opens the multicolor land-cover overlay, a water request opens the water overlay, and a building request opens the building overlay. Previously, the first generated overlay could be the water layer even for a land request.

Three RGB aerial scenes that exposed false positives were rechecked. On the forest/cropland scene shown in the supplied screenshot, an earlier failed-model run painted 35.74% as water; the functioning two-model route now reports 0.00% water and colors woodland, agriculture, and bare/pervious ground separately. On the golf-course scene, reported water fell from 6.08% to 0.025% of valid pixels, and 10.57% received a bare/pervious color. On the parking-lot scene, reported water is 0.00%, while paved surfaces remain in the road/paved class. These are scene-level behavior checks, not ground-truth accuracy estimates. A small blue patch remains on the golf scene; RGB alone cannot reliably resolve every dark patch. The live API now records the withheld-candidate fraction and marks the golf result `low_confidence` because the two models disagreed on almost all initial water pixels.

The current `.env` has optional localhost model-service addresses. The imported surface pipeline defaults to offline mode, so those services do not influence its results. The current project's non-surface routes retain their existing model configuration. The Windows launcher does not start mock servers. `SATQUERY_SURFACE_WATER_CHECKPOINT` optionally overrides the imported ten-band bundle; `SATQUERY_WATER_CHECKPOINT` remains the current project's earlier water-model setting.

Use `scripts/setup_windows.ps1` for a local environment and `run.bat` to launch the current API and dashboard. On Windows, setup temporarily assigns a short drive alias to this folder so large Python packages can install despite the long project path; it removes the alias when done. The selected surface regression tests are in `backend/tests_integrated`, and the routing boundary test is in `backend/tests/test_surface_routing_boundary.py`. Run `python -m pytest backend/tests backend/tests_integrated` with the project's Python environment. Run `python scripts/verify_integrated_pipeline.py <image>` to check actual surface inference, building labels versus the reported count, mask exclusion, and manifest agreement.

For the georeferenced aerial reference image from `D:\Sat1`, `artifacts/integrated-aerial-local-pinned/verification.json` records FLAIR-HUB, RF-DETR, and Deepness as models actually used and 179 estimated buildings in the current project's local environment. The reference environment produced 178 on the same scene. This one-building difference means the counts are estimates sensitive to runtime and model postprocessing; neither is a surveyed count or a measure of general accuracy across sensors and locations. The verification confirms integration and output consistency. The system marks this scene low confidence and includes model-specific limitations in its answer and report.

The frontend production build passed. The local Python environment includes OpenCV for the current project's registration and SAR routes. The copied surface code retains its own regression tests for surface-specific scientific and spatial invariants.
